# PM-002 — Проверка клиентского стека и архитектурные решения

- **Порядок:** 2; этап 1 — Требования, стек, дизайн и контракт.
- **Приоритет:** P0.
- **Состояние:** planned.
- **Зависимости:** PM-001.
- **Открытые вводные:** использовать зафиксированные решения; новые блокеры описывать явно.
- **После этапа:** G01 — презентация и минимум 10 отдельных вопросов.

## Цель

Выбрать практически пригодный стек с максимальным использованием Python.

## Объём и порядок работы

1. Прочитать регламент, решения, зависимости и связанную GitHub issue.
2. Сравнить Python/Flet и альтернативу для Web/Android на одном экране: карточка товара, новости, график, Google-вход, deep link, offline-кеш. Сделать минимальную сборку Android и доказательство интеграции домашнего новостного виджета/уведомлений. Оценить Web-доступность и размер/запуск клиента. Обосновать нативные компоненты. Зафиксировать модульный backend, PostgreSQL, worker и схему развёртывания.
3. Выполнить критерии ниже, обновить документацию и пояснительную записку.

## Ожидаемые результаты

ADR со стеком, воспроизводимый spike, результаты на Android и Web, перечень SDK/аккаунтов и версия инструментов.

## Критерии приёмки

- [ ] Есть проверяемая Web-сборка и Android-прототип; виджет технически доказан либо выбор стека изменён. Серверная сессия Python не выдаётся за клиентский offline runtime. Непроверенное явно оставляет решение открытым.
- [ ] Проверки выполнены и их фактические результаты сохранены.
- [ ] CHANGELOG, STATUS, документация и GitHub issue обновлены; нет секретов в поставке.
- [ ] Пояснительная записка `docs/task-results/PM-002.md` содержит изменения, ограничения и доказательства.

## Проверка

Сборка из чистого окружения; открытие URL в браузере/приложении; проба виджета; доступность, offline и возврат Google-входа.
