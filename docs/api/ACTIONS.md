# Implemented request and bot delivery API

PM-010 · local pilot. Actions request one product; no cart, charge or payment.
The catalog bot in PM-011 will demonstrate confirmed and failed outcomes.

## Client: create and read a request

`POST /v1/channels/{channel_id}/actions`, session/Origin/CSRF, with a stable
`Idempotency-Key` (8..128 ASCII letters, digits, underscore or hyphen):

```json
{"action_id":"request_soap","resource_id":"soap","observed_source_revision":1,"quantity":1}
```

The caller needs current read access to the published channel. The server checks
the published product/action binding, resource type, current availability and
observed revision. Client price, bot/user IDs and unknown fields are rejected.
The G02 pilot supports only `request_purchase`/`Request purchase`, quantity=1.
It atomically commits the request, its stable event identity and an outbox hint
before returning 202 `ActionRequest`, state queued. This is not an order/payment
confirmation. IDs are generated by the server.

Idempotency is scoped to user + channel + key. Same body returns the same request
with its current status; a different body returns 409 idempotency_conflict. Current
source access is rechecked on replay, even after success. Changed product/layout
does not turn a retry into a new request. A new request with stale observed revision
gets 409 resource_changed; unavailable product gets 409 resource_unavailable;
disabled/mismatched action gets 422 action_not_allowed.

`GET /v1/action-requests/{action_request_id}` reads only the requesting user's
request while source access remains valid. A business owner cannot read another
user's private status through this route. Returned fields: stable IDs, state,
created_at/updated_at and safe plain-text summary. No private bot diagnostics.

## Bot: GET, durable ACK, result

Use the bot operational Bearer key; no platform user session or database access.

1. `GET /v1/bot/events?limit=100&wait=25` requires events:read and returns this
   bot's unacknowledged nonterminal events. Repeated reads do not acknowledge,
   lease or delete an event. actor_ref is a server-HMAC pseudonym scoped to the
   bot; it contains no platform username, password, email or session token.
2. Save event_id/action_request_id and execution state durably in the bot's own
   store. Then `POST /v1/bot/events/{event_id}/ack` with `{}`, events:ack scope.
   Repeat ACK returns the original acknowledged_at. ACK removes the event from
   pending delivery; it does not confirm a purchase or finish the request.
3. Before external effects, obtain a successful ACK and use the action request ID
   as the external idempotency key. If an external call has an ambiguous outcome,
   reconcile status instead of executing again blindly.
4. `POST /v1/bot/events/{event_id}/result`, events:result scope:

```json
{"result_id":"soap-result-001","result_revision":1,"state":"confirmed","summary":"Demo request confirmed. No payment has been taken."}
```

Allowed result states: processing, confirmed, failed. Each result_id is unique
within the bot, including across events; reuse it with exactly the same body when
retrying. An optional opaque external_reference is stored for reconciliation and
never returned in client status. Never put credentials/private diagnostics there.
New revisions must increase; result before ACK gets 409 ack_required. Confirmed,
failed and cancelled are immutable. A repeated old progress result returns current
authoritative status, never regresses it. Conflicting body/event ID gets 409
idempotency_conflict, stale new revision gets 409 stale_result_revision.

`GET /v1/bot/requests` lists all nonterminal requests, including already ACKed
events, for reconciliation after a restart. It uses the BotEvent shape. Compare
with the bot's durable inbox; do not infer that absence from pending GET means
success. A terminal result is required to finish a request.

## Scan and wait rules

Default limit=100, range1..100. Signed cursor binds bot and operation, fixes an
upper sequence and expires after 60s. Continue non-null next_cursor; after null
start a new scan without a cursor so new arrivals are not skipped. Later ACKed or
cancelled entries disappear; newly created entries beyond the fixed bound wait
for the next scan. Another bot/operation or modified cursor fails 400; expiry410.

wait=0..25, default0, allowed only on the first events page. Async waiting keeps no
database connection, transaction, row lock or synchronous thread occupied between
checks. The key is rechecked approximately once per second; revocation interrupts
the wait. This is bounded polling, not a proven 100-bot long-poll capacity result.

## Revocation, uncertainty and retention

Grant removal and public-to-selected publication recompute effective access.
Removing a grant from a public channel does not remove public read rights. Requests
for users who lose access are cancelled if unACKed; already ACKed unresolved work
becomes unknown. ACK and revocation serialize on the channel lock. The bot must
not execute after a rejected ACK. It may report a real outcome for previously
ACKed work while its own key/channel remains valid, even after the user's access
was revoked. The revoked user cannot read or replay the private request.

Account deactivation applies the same rule to that user's requests. Disabling a
channel/bot preserves unresolved work as unknown for operator reconciliation and
blocks further bot calls for that channel. The platform does not claim to reverse
external effects. There is no operator resolution UI yet.

No ACK for 60s, or no progress/result for 5min after ACK/progress, shows unknown.
The maintenance worker persists timeout transitions and status hints every 60s;
reads also derive uncertainty from timestamps if the worker is stopped. Unknown
is nonterminal and recoverable: a late result may become processing/confirmed/failed.
No background process automatically repeats business effects.

Terminal requests, their result receipts and idempotency keys remain 30 days after
the terminal transition. Unresolved work remains until resolved. Pruning deletes
only bounded terminal batches and preserves unresolved deduplication. Past the
retention window an old key no longer prevents a new request; do not recreate an
uncertain historic operation. Ingestion history/dedup also remains 30/30 days.

## Limits and verification

MARKETOB_ACTION_RATE_LIMIT=30/min/user; MARKETOB_BOT_ACTION_RATE_LIMIT=600/min/bot
for ACK/result; GET shares MARKETOB_BOT_READ_RATE_LIMIT=60/min/bot. Limits survive
API restart and return Retry-After on429. Internal long-poll checks consume one
logical read allowance, not one allowance per second. Requests still obey the
general write/session limits and 256KiB JSON transport limit. Back off on429/503
or ambiguous network failure using the same message/action/result identity.

PM-022 limits each bot to1,000 unresolved requests across all its channels.
Concurrent admission is serialized by the bot row lock. Exact idempotent replay
still reads the existing request at capacity. A terminal result frees a slot;
ACK/unknown do not. A full queue returns429/Retry-After60 before inserting anything.
The operator must restore/reconcile the bot; unresolved work is never silently
deleted to make room. Outbox backpressure can also return429 for state changes.

`tests/test_actions.py` uses real PostgreSQL to exercise retries, before/after ACK
recovery, result ordering, user/bot isolation, rights changes, concurrent races,
timeouts, retention and injected outbox rollback. `python -m scripts.smoke_actions
--phase before`, restart the API/database, then `--phase after` proves persistence
over actual HTTP. Its ignored .local state contains synthetic credentials; never
publish it. The after phase deactivates its own account and removes that state.

Docker CI runs several disposable identities on one IP with explicit auth quota
100; normal Compose defaults to10. Default rate enforcement is tested separately.
Outbox hints and foreground delivery are implemented in PM-018. Web confirmation
and request status are available in the working PM-013 client.
