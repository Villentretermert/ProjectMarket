# MarkeTOB API 1.0 — normative local pilot contract

**PM-004 specification, not a deployed service.** Backend implementation starts in PM-005–012. The executable reference model checks protocol examples only; it does not prove durability, concurrent transactions, HTTP authentication or load capacity. All example content is synthetic. The contract is independent of Telegram.

Machine-readable sources: [OpenAPI 3.1.1](../../packages/contracts/src/contracts/openapi.json), [JSON Schema 2020-12 bundle](../../packages/contracts/src/contracts/schemas.json), [Python generator](../../packages/contracts/src/contracts/build_contract.py), [valid/invalid examples](../../packages/contracts/src/contracts/examples/cases.json). `$defs` names identify the validation target. `required`, numeric/string/array bounds, descriptions and `additionalProperties: false` define each field. Unknown fields are rejected, not silently executed or retained. [Quickstart](QUICKSTART.md) walks through the complete lifecycle.

## Transport, identity and ownership

- JSON is UTF-8, `Content-Type: application/json`; maximum decoded request body is **262144 bytes**, including envelopes. Reject duplicate JSON keys, nonfinite numbers and unsupported content encodings. Do not render strings as HTML. No inbound file uploads, base64 images, remote image proxy or bot-supplied URLs in v1.
- HTTP is allowed only on loopback development endpoints. Remote bot/client deployments require HTTPS. Default local API binding is 127.0.0.1, not a public interface. Cross-origin browser requests are denied unless the exact origin is configured; wildcard credentials are prohibited.
- `POST /v1/auth/register` creates a local user; the same user can own bots/channels and consume other channels. Login creates an opaque server-side session. Cookie `marketob_session` is HttpOnly, SameSite=Strict, Path=/; Secure for HTTPS. Loopback development is the explicit Secure exception. Lifetime is 24 hours, no silent indefinite renewal. Logout invalidates the session and clears the cookie.
- Registration/login validate Origin against exact configured UI origins; other unsafe session requests require `X-CSRF-Token` bound to that session as well. `GET /v1/auth/session` returns user metadata and the CSRF token. Session/cookie/password values must never be logged, embedded in a share or given to a bot. Login failures use the same safe error for nonexistent users and wrong passwords; implement password hashing/rate limits in PM-006.
- A B2B owner creates a bot with `POST /v1/bots`. The response contains a unique **15-minute, one-use registration credential**. Exchange through `Authorization: Bearer …` on `/v1/bot-registrations/exchange`; it cannot call operational routes. Exchange consumes the credential and creates a 90-day operational key atomically. Raw keys appear only at issuance, with `Cache-Control: no-store`. Server stores verifiers/digests, not plaintext secrets.
- A lost exchange response is recovered by the owner issuing a new key, not by replaying a consumed bootstrap credential. Renew registration invalidates outstanding bootstrap credentials; it does not silently revoke existing operational keys. Key creation with `replaces_key_id` atomically revokes that key with **no overlap**. Key revocation is checked before every request, including duplicate messages. Bot revocation disables all keys, channels and new actions. Read inventory exposes only key metadata/prefix.
- Initial exchange grants `messages:write`, `events:read`, `events:ack`, `events:result` to that bot. Owner-issued keys may narrow these scopes. A bot key cannot create users, change grants, publish a channel, access another bot's events or write a foreign channel. Identity is derived from the key, never a body `bot_id`. Every object route checks ownership/membership, not just authentication.
- Local accounts work without Google/Firebase. Native session handling is subject to the deferred Android verification. OS push registration/device endpoints are deliberately absent from v1 local scope; adding them requires a versioned contract amendment.

## Channels, data and interface versions

An owner creates a draft channel bound to an owned bot. The bot can send data into that draft. Owner draft routes define title, visibility, layout and allowed actions; publish validates existing resources, compatible block types, unique IDs and action references before exposing a version. Only the owner publishes. Consumers see published versions only.

| Field | Meaning and update rules |
|---|---|
| `schema_version` | Exactly `1.0` in this contract. Unsupported version → 422 `unsupported_schema_version`. No best-effort downgrade. |
| `template_version` | Monotonic page layout version. Creation starts at 1. Draft/page replacement supplies expected current version and proposed next version=current+1; conflict → 409. A new personal page uses expected=0 and template=1. Publishing does not silently increment the draft version. |
| `source_revision` | Bot-owned integer, strictly increasing per `(bot, channel, resource)`, including deletes. It controls source ordering; wall-clock timestamps do not. |
| `data_revision` | Server-owned monotonic channel change counter, advanced with committed snapshot/event and outbox. It is separate from layout and source versions. |

`kind=text` contains `News` title/body and normalizes to a news record. `kind=data` contains exactly a typed news/product/chart payload and replaces that resource. `kind=event` is a notification hint (`news.published` or `catalog.changed`) for an existing resource; it never acts as a business result or implicitly updates a snapshot. `kind=delete` creates a revision tombstone and removes source content. A higher revision can explicitly recreate a resource; replay of an older revision cannot.

`message_id` is unique per bot for at least **30 days**. Same ID and same validated body return the original receipt without a new revision. Object key order/whitespace do not matter; altered values or numeric representation conflict with 409 `idempotency_conflict`. New ID with source revision ≤ current returns 409 `stale_source_revision`. Authenticate and check channel ownership before returning a cached receipt. Within a DB transaction, commit receipt, latest record/tombstone, revision and outbox before returning HTTP 200. A receipt proves acceptance, not bot-to-client display time. Event receipt also advances the channel revision. No accepted response may be emitted before durable commit.

News body/product description: ≤20000 characters. Charts: ≤5 named series, ≤1000 points each, finite values, unique series names and strictly increasing x coordinates per series. `x_kind=time` uses epoch milliseconds; other x values are numeric, not categorical. Units/axis labels are explicit. Price uses integer minor units and a supported ISO currency mapping; pilot supports EUR/USD (2 minor digits) and RUB (2), with additional codes requiring server configuration/validation. This is display data, not an executable offer or charge.

Layouts have ≤50 blocks with stable unique IDs. Source binding is only `(channel_id, resource_id)`. B2B layouts bind their own channel; My Space may reference multiple channels. Allowed views: news article/compact; product card/list; chart bars/line/table. Product actions must refer to owner-approved action definitions for that product. No SQL, JSONPath, JS, Python, arbitrary HTML/CSS, user roles, raw source payloads or secrets are permitted. Empty layouts are valid. Unknown component/view/version fails explicitly before import/publish.

## Access, shares and caching

Public published channels allow anonymous read. Saved channels, actions, My Space and import require a session. Selected-member channels require owner or explicit read grant to an existing user. Grants do not assign B2B ownership. Unauthorized consumers receive generic 404 `source_unavailable` without private title/timestamps. Owners receive specific validation errors only for their own objects. Favorites and source references never grant access.

Sharing stores an immutable layout-only snapshot server-side; the 32-character base64url code has 192 bits of entropy. It is a locator, **not encryption** and not a source authorization token. Do not place private titles or data in the copied source references. Preview/import resolve permissions independently; inaccessible blocks receive placeholders, without fetching private payloads or update times. Imports create a new personal page with version 1. Source blocks remain live references, not copied grants. Revoke/expiry prevents new imports; it does not delete previously imported layouts. Codes work only against their issuing server. A friend's device cannot reach a loopback-only server; shared network deployment/HTTPS is a later explicit setup step.

Session, key, private data and all v1 responses use no-store at the HTTP layer. An application-managed private offline cache is bounded to 15 minutes since the last successful access check, cleared immediately on logout/known revocation; on expiry show Access required and hide content. Public snapshots may be displayed stale with source time. Actions are disabled offline and always revalidated online. Source deletion removes private content, shows Source unavailable for that block and leaves unrelated blocks usable. Tombstones retain only ID/revision as long as the channel exists; channel identifiers are never recycled.

## Requests, GET, ACK and business results

1. Client POSTs an `ActionInput` with `Idempotency-Key`, current observed source revision and quantity. Server rechecks current user access, published action/resource mapping, availability and revision. Stale item →409 `resource_changed`; unavailable item →409 `resource_unavailable`; no allowed action →422 `action_not_allowed`. No request/event is created on failure.
2. Atomically commit request, bot event and outbox. HTTP **202 means queued**, not purchased/paid. Scope idempotency by `(user, operation, channel, key)`; same body returns the existing request, changed body →409. Retain records ≥30 days and for the entire unresolved lifetime. Recheck current access even on replay. The bot sees a bot-scoped pseudonymous `actor_ref`, quantity and IDs, never user credentials or full profile.
3. `GET /v1/bot/events?limit=100&wait=25` returns only that bot's unacknowledged events. GET creates no receipt/lease and never deletes an event. It may be retried safely. Default limit=100; limit range1–100, wait0–25, default0. `wait>0` is allowed only without cursor; otherwise400. Cursor binds bot, filter, fixed upper sequence and position, authenticated by the server; lifetime **60 seconds**. A page skips subsequently ACKed/cancelled records but cannot skip new records inside its fixed scan. Non-null cursor continues that scan; null means start a fresh scan **without cursor**. New arrivals beyond its upper bound appear next scan. Expired cursor →410 `cursor_expired`; discard it and restart. Never persist a terminal cursor as a consumer offset.
4. Delivery is **at least once**. A crashed/unresponsive bot polls again without cursor; all unacknowledged events are eligible again. Use one active poll loop per bot; duplicate delivery under concurrency is allowed. The bot stores `event_id`/`action_request_id` durably before ACK. Persist its own execution state before creating external side effects. External services must support idempotency or status lookup. Do not blindly repeat an ambiguous purchase/request effect.
5. `POST .../ack` with `{}` is idempotent durable receipt. It removes that event from pending GET pages but **does not change queued to confirmed**. Bot must report `processing` or a terminal `confirmed`/`failed` result separately. `GET /v1/bot/requests` lists all nonterminal events, including ACKed ones, for recovery/reconciliation. It uses the same bounded scan rules. Retrying ACK returns the original timestamp. If result arrives before ACK,409 `ack_required`.
6. Result has unique `result_id`, increasing `result_revision`, state and safe summary. Same ID/body is a no-op; changed body409. Lower/equal new revision409. Allowed transitions: queued→processing/confirmed/failed, processing→processing/confirmed/failed, unknown→processing/confirmed/failed. Confirmed/failed/cancelled are terminal and immutable; a conflicting new result returns409 `terminal_conflict`. A duplicate old progress result returns the current authoritative request status without regression.
7. No ACK after60 seconds or no progress/result for5 minutes produces user-visible **unknown**, not automatic failure or confirmation; unresolved work remains recoverable. A late result may resolve unknown. Bot must reconcile its durable log/external reference before deciding whether to execute anything again. Pending records are never silently aged out. Operators can investigate stuck work; there is no automatic retry of business effects by MarkeTOB.
8. Revoking a user grant cancels undelivered/unACKed requests atomically with invalidation. The bot must receive successful ACK **before** external execution; ACK vs revoke race is serialized. Already ACKed work may already have happened: mark unresolved work unknown and reconcile, never promise rollback. Bot can record its actual result while its own key/channel ownership remains valid. The revoked user cannot read private request content or issue/replay actions. Owner bot/channel revocation blocks subsequent bot calls and leaves unresolved records for owner/operator reconciliation, never invented success.

Terminal results and action idempotency receipts are retained30 days; unresolved requests and their deduplication records are retained until resolved. Clients must use stable retry keys. Requests after the retention window have no automatic duplicate protection; do not recreate an uncertain old action automatically.

## Live updates, list cursors and quotas

v1 uses authenticated **polling**, target interval2 seconds while foreground/online. `/v1/updates` carries only revision hints and access invalidations. Establish a cursor first, then fetch current snapshots, then poll from that cursor; this closes the bootstrap race. Without a cursor return current watermark and no historical hints. Cursor is user/session-bound, authenticated, retained10 minutes. Expired/invalid-history cursor →410 `resync_required`; obtain a new watermark and refetch snapshots. New access is checked on every response; revoke events contain only a previously known target ID. Client clears unauthorized snapshots on invalidation or a forbidden read. PM-018 measures actual latency; no current implementation or SLO is claimed.

Other list routes use caller-bound 60-second fixed scans and nullable next_cursor, limit1–100 default100. Invalid/tampered cursor400 `invalid_cursor`; another identity cannot reuse it. Import POST and action POST require idempotency; other creates may produce duplicates on an ambiguous transport failure, so inspect owned inventory before retry. PUT/DELETE are idempotent within authorization; compare versions on layout writes. Delete of an already removed owned item returns204; unknown foreign IDs return404.

Initial configurable quotas: message ingest60/minute/bot (burst60), aggregate1000/minute (burst1000); bot GET events/requests60/minute/bot; ACK/result600/minute/bot; actions30/minute/user; ordinary reads120/minute/session; login/register10/minute/IP; bootstrap exchange10/minute/IP; all other writes60/minute/user. These are deployment defaults, not measured capacity. Return429 and Retry-After seconds; bounded exponential backoff (1,2,4…30s plus jitter) for429/503/network failure. Retry only with the same message/action/result identity; do not generate a fresh business action. Payload>256KiB413, including decompressed limits. Raw ingest history7 days, audit90 days without secrets/private payload, backups7 daily. See [pilot targets](../requirements/PILOT_TARGETS.md).

## Errors and compatibility

All errors contain `code`, safe English `message`, server `request_id`, `retryable`; no stack trace or secret body. Clients branch on code/status, not message text. Cache-Control:no-store applies to errors too.

| HTTP | Stable codes / client action |
|---|---|
| 400 | invalid_json, invalid_cursor, invalid_query; fix input, do not loop |
| 401 | invalid_credentials, expired_credentials; authenticate/reissue key, never log the value |
| 403 | insufficient_scope, csrf_failed; no automatic permission escalation |
| 404 | source_unavailable, request_not_found, object_not_found; clear inaccessible data |
| 409 | idempotency_conflict, stale_source_revision, version_conflict, resource_changed, resource_unavailable, ack_required, terminal_conflict, stale_result_revision, request_cancelled; reconcile before retry |
| 410 | cursor_expired, resync_required, share_expired, share_revoked; restart scan/resync or request a new share |
| 413 / 415 | payload_too_large / unsupported_media_type; correct the request |
| 422 | invalid_payload, unsupported_schema_version, incompatible_view, duplicate_block, duplicate_series, invalid_chart_order, unsupported_currency, action_not_allowed; use supported schemas |
| 500 | internal_error; outcome may be ambiguous, reconcile/retry with the same identity |
| 429 / 503 | rate_limited / temporarily_unavailable; retryable=true, bounded backoff; same identities |

1.0 is a closed schema: additions that older validators reject require an advertised new schema version and explicit client support. No silent coercion of incompatible templates. Endpoint major version `/v1` changes for incompatible resource/authorization semantics. Product implementation must generate or verify against these checked-in artifacts; future amendments update examples, tests, protocol, changelog and issues together.
