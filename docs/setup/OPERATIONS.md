# Локальная эксплуатация MarkeTOB

PM-022. Команды выполняются из ProjectMarket. Инструменты не отправляют сообщения
или данные во внешние службы. Планировщик автоматических проверок не установлен.

## Отчёт и сигналы

Для Python-стенда укажите в локальном `.env`
`MARKETOB_LOG_DIRECTORY=.local/logs`, запустите API и отдельный maintenance worker.
Файлы `api.jsonl` и `worker.jsonl` ротируются: до пяти файлов по10MiB на процесс.
Для Docker логи ограничены драйвером local и читаются через `docker compose logs`.
Сырые PostgreSQL диагностические логи старого native-стенда не публикуются.

```powershell
.venv-dev/Scripts/python.exe -m scripts.operations --connection-file .local/postgres-dev/connection.json --logs .local/logs --minutes 5 --disk-path .local/postgres-dev
```

Без `--connection-file` используется `MARKETOB_DATABASE_URL` из окружения/.env.
`--schema` нужен только для изолированного тестового пространства. Пароль не
передаётся аргументом командной строки. Команда делает только чтение, выводит JSON
и завершается кодом0 при отсутствии сигналов,1 при сигнале,2 при недоступности
проверки. Если окно журнала уже удалено ротацией или сервер только запустился,
`log_window_incomplete` запрещает выдавать неполную выборку за полный период.
Метрики логов содержат p95/p99/max по шаблонам маршрутов и отдельные HTTP-коды.

Для DB gauges внутри Docker без копирования пароля на хост:

```powershell
wsl -d Ubuntu -- docker compose --project-name marketob-pm021 --env-file .local/pm021/docker.env exec -T api python -m marketob_api.operations
wsl -d Ubuntu -- docker compose --project-name marketob-pm021 --env-file .local/pm021/docker.env exec -T db df -h /var/lib/postgresql
```

Для своего проекта подставьте его имя/env-file из инструкции поставки. В Docker
HTTP-логи доступны через `compose logs api`; DB gauges команда читает независимо.

| Сигнал | Порог | Действие оператора |
|---|---|---|
| worker_stale | Нет успешного прохода или старше130с | Проверить worker/БД, восстановить worker; не удалять очередь |
| outbox_delayed | Старейшее ненумерованное событие >120с | Проверить worker и запросы `/updates`, затем отставание |
| outbox_capacity | >16 000 ненумерованных | Восстановить обработку до admission20 000 |
| outbox_retention_capacity | >200 000 записей outbox | Проверить очистку до admission250 000 |
| bot_not_acknowledging | Нерешённая заявка без ACK >60с | Проверить конкретного бота через Studio/его собственные логи |
| requests_need_reconciliation | Есть unknown | GET unresolved, сверка реального результата, идемпотентный result |
| bot_queue_capacity | >800 нерешённых у одного бота | Исправить бота до предела1 000; не создавать дубликаты заявок |
| history_capacity | >80% лимита строк/байтов хотя бы у одного бота | Согласовать ёмкость; остановить лишний поток, сохранить принятую историю |
| retention_overdue | История старше30дней+10мин | Проверить worker и доступ к БД |
| api_errors | 5xx ≥1% в окне | Сопоставить request_id и состояние хранилища |
| api_latency | ingest/read p95>500мс или p99>2с | Проверить CPU, диск, пул, locks; повторить профиль после исправления |
| disk_reserve_low | Свободно <10GiB или <15% указанного тома | Ограничить новый поток, перенести/расширить хранилище; проверить backups |

`--disk-path` должен указывать на том фактической БД. Для WSL PostgreSQL нужно
также проверять свободное место Windows-тома с виртуальным диском. Метрики CLI
показывают число/возраст очередей и unknown, размеры схемы/JSON истории и heartbeat.
Они не содержат payload, ключей или персональных имён.

## При переполнении

Бот повторяет тот же message ID/body после Retry-After. Запрос, получивший429,
не считается принятым. Уже подтверждённое чтение квитанции доступно при заполненной
истории. На стороне клиента неизвестный исход проверяется через прежнюю заявку.
Заявки не удаляются из очереди ради освобождения места без результата бота.

Квоты скорости: 60 сообщений/мин на бота и1 000 суммарно, с token-bucket запасом.
Отклонённый по индивидуальной квоте бот не расходует общий запас. Ограничения
хранения: 256MiB/100 000 history rows,10 000 source records/tombstones и1 000
нерешённых заявок на бота. Подробнее: [ADR-0015](../adr/0015-operations-capacity.md).
30 дней являются сроком хранения, а не гарантией вместимости30 дней пикового потока.

## Нагрузочная проверка

```powershell
$env:MARKETOB_BROWSER_CHANNEL='msedge'
.venv-dev/Scripts/python.exe -m scripts.live_load --connection-file .local/postgres-dev/connection.json --bots 100 --seconds 1800 --burst --output .local/pm022/L2
```

Используются100 независимых HTTP-ботов,100 браузерных контекстов/аккаунтов,80%
news/product ≤4KiB и20%chart ≤32KiB.10% клиентов отправляют одну заявку в минуту.
30мин ровного потока,60с предложения3 000 сообщений/мин, затем ограниченное
восстановление с повтором429. В burst промежуточные ревизии могут объединяться в
актуальном snapshot; проверяются все квитанции и итоговое состояние100 клиентов.
Для steady отдельно проверяется каждая отображённая ревизия.

API/worker рестартуют после измерения, число подтверждённых записей сверяется.
Измерения host CPU/RAM относятся ко всему компьютеру, включая генератор браузеров
и другие приложения. Это не квота ресурсов облачного сервера. Short rehearsal и
подготовка клиентов не заменяют L2. Тест удаляет только свою случайную lab-схему.
