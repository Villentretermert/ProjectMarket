# ADR-0008 · Очередь заявок и независимые ACK/result

22 октября 2026 · PM-010 · принято на основе PM-004 и ответов G02.

action_requests хранит заявку и стабильную delivery identity в одной строке.
Отдельный брокер пока не нужен: GET выбирает durable очередь PostgreSQL. Создание
заявки и outbox фиксируется одной транзакцией; никакого окна между двумя БД нет.
action_results хранит дедупликацию результатов по bot/result_id, а terminal_at
управляет 30-дневной очисткой. Незавершённая работа не удаляется по возрасту.

GET не является доставкой с подтверждением. Бот сохраняет inbox у себя, получает
ACK, затем исполняет и сообщает processing/confirmed/failed. Внешние операции
требуют idempotency/reconciliation со стороны бота. Автоматического exactly-once
внешнего эффекта платформа не обещает. Unknown означает отсутствие известного
результата, а не отказ или успешную покупку.

Блокировки идут organization → bot (если нужен) → channel → request. Создание
заявки берёт bot key-share до channel, чтобы FK не инвертировал порядок отзыва
бота. Deactivation не меняет user/org ключи и использует NO KEY UPDATE: это
останавливает сессионные операции, сохраняя возможность записать FK status hint
для реального результата бота. Worker блокирует по одному channel на транзакцию
до изменения request и outbox. Grant блокирует целевого пользователя до канала, как его deactivation. Long poll не держит транзакцию во время ожидания.

На отзыве grant/видимости unACKed отменяется, ACKed становится unknown; результат
ACKed работы допустим после отзыва пользовательского доступа. Отключение самого
бота/канала блокирует его API и оставляет unresolved для оператора. Наблюдение
пока через API/БД тестового стенда; owner reconciliation UI не входит в PM-010.

[Контракт и примеры](../api/ACTIONS.md). Альтернатива «GET удаляет событие» отвергнута:
падение бота между чтением и записью теряло бы заявку. ACK как бизнес-успех отвергнут:
доставка сама по себе не доказывает исполнение.
