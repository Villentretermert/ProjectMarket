# PM-023 · отзыв доступа при заполненной очереди

24 октября 2026. Предложение исправления finding
`resource-exhaustion.membership-outbox-fanout` (scan
`358f6f14-3d8a-4ada-8482-046a4f86966f`). Исходный широкий патч отклонён
автоматической проверкой; ниже уточнён механизм и проверены его базовые свойства.

Обычная запись данных сохраняет прежний outbox и backpressure. Изменение прав
вместо N уведомлений резервирует одну позицию в существующем `delivery_state`:

```sql
UPDATE delivery_state
SET watermark = watermark + 1, retention_floor = watermark + 1;
```

Команда выполняется в той же транзакции, что grant/membership/deactivation.
Старый cursor получает уже существующий `410 resync_required`; клиент получает
новый watermark, затем повторно читает snapshots, избранное и статусы с текущими
правами. Маркер не является пользовательским событием, не содержит персональных
данных и не расходует ёмкость очереди. Dispatcher использует тот же row lock,
поэтому следующие события получают больший ID. Ранее принятые данные/receipts
и строки чужих событий не удаляются.

Ограничение пилота: изменение прав заставляет пересинхронизироваться все открытые
сессии сервера. Это может повысить нагрузку при частых реальных изменениях прав;
неизменные PUT не создают маркер. Проверка L2 остаётся отложенной, SLO после этого
изменения не утверждается. Перед внешним масштабированием возможны отдельные
инвалидации по пользователям/workspace.

Необходимые изменения:

- Общий helper для одной атомарной операции; без изменения JSON Bot API.
- Grants, membership, удаление аккаунта/бота/канала и сужение public → selected
  используют маркер; обычная публикация/приём данных сохраняют outbox.
- Reconciliation при отзыве сохраняет состояния queued/cancelled/unknown, но не
  создаёт N уведомлений для уже недоступных заявок. Его вызывающий маршрут создаёт
  один маркер. Обычные bot result/timeout notifications остаются прежними.
- Retention обновляет floor через `greatest(retention_floor, deleted_prefix)`,
  чтобы очистка старого prefix никогда не уменьшила уже установленную границу.
- Проверить все перечисленные revoke-маршруты при полной очереди, текущие роли,
  восстановление UI после410, сохранность receipts и монотонность ID.

Предварительный эксперимент в отдельных временных PostgreSQL schemas:
3/3 PASS — 20 000 pending rows не мешают marker+grant DELETE; откат возвращает
и права, и delivery_state; поздний commit после маркера получает новый больший ID.
Эксперимент не менял исходники приложения и не является сквозной приёмкой патча.

После эксперимента уточнённый патч также отклонён автоматической проверкой:
изменение нескольких критических маршрутов требует явного разрешения, а SQL-модель
не подтверждает безопасность интеграции. Ни одна из двух версий широкого патча
не применена. Разрешение запрашивается на реализацию описанного механизма,
интеграционные и браузерные проверки всех revoke-путей и сохранение результатов;
оно не означает автоматическую приёмку PM-023 или возобновление отложенного L2.
