# Регламент совместной работы

Версия 1.0 · 19 октября 2026 · источник: прямые указания владельца проекта.

## Обязательные правила

1. **При каждом изменении вести лог.** В `CHANGELOG.md` фиксировать дату, ID задачи, что изменилось, зачем, что проверено и известные ограничения. Одно связное изменение — одна запись; не требуется запись на каждую строку кода.
2. **Показывать дизайн визуально и текстом.** Перед разработкой пользовательского сценария показать макет и объяснить действия B2B/B2C. После реализации показать фактический результат и отличия от макета. Прототипы помечать как прототипы, демонстрационные данные — как демонстрационные.
3. **Делить крупную работу на этапы.** У каждой задачи стабильный ID PM-NNN, цель, порядок, приоритет, зависимости, результат и критерии приёмки.
4. **Делать задачи последовательно и проверяемо.** Перед началом читать зависимости; после завершения выполнять подходящие проверки и писать пояснительную записку с компонентами, файлами, решениями и результатами тестов. Не заменять проверку устройства предположением.
5. **Вести задачи в GitHub Issues.** Создавать issue до реализации, описывать цель, порядок, приоритет, связи и ожидаемые результаты. По окончании записывать фактические результаты, commit/PR, проверки и ограничения. Закрывать issue только при выполнении критериев. Если GitHub недоступен, сохранять локальный проект задачи и явно сообщать о несинхронизированном состоянии.
6. **После каждой четвёртой завершённой задачи проводить презентацию.** Показать сделанное, результаты и проверки, оставшуюся работу, следующий этап и причину выбора. Объяснить ключевые участки кода, компоненты и сущности; показать схему системы с отметками «готово / частично / не сделано». Сохранять презентацию и пояснения в `docs/reviews/GNN/`. Формат по умолчанию: PPTX/PDF плюс Markdown с доказательствами; если среда не позволяет экспорт, явно сообщить, что доступен только Markdown.
7. **После презентации, до следующей задачи задать минимум 10 отдельных наводящих вопросов.** Не объединять их в одну анкетную карточку. Сохранить ответы, скорректировать план и продолжать после ответа владельца либо его явного указания продолжить с допущениями. Не трактовать молчание как одобрение.
8. **Максимально использовать Python.** Backend, схемы, SDK, пилотные боты и автоматизация — Python по умолчанию. Frontend на Python является приоритетным вариантом, но выбирается после проверки Android/Web/виджетов. Необходимый нативный код или другой язык обосновать и зафиксировать решением. Код сопровождать короткими комментариями там, где требуется пояснение.
9. **Хранить этот регламент отдельно и перечитывать перед каждой задачей.** Ссылка на него находится в `AGENTS.md`. Текущие прямые указания владельца имеют приоритет; изменения регламента также записывать в журнал.

## Учёт задач и контрольных точек

- Подготовка этого плана не считается четырьмя выполненными задачами. На старте выполнено 0 из 24 задач пилота.
- Счётчик увеличивается только при приёмке полноценной PM-задачи, а не при коммите, правке документа или подзадаче. После 4, 8, 12, 16, 20 и 24 задач обязательны G01–G06. Для четырёх задач развития предусмотрена G07.
- Если задачи выполняются в ином согласованном порядке, презентация всё равно требуется после каждых четырёх завершений; нельзя обходить её переименованием задач.
- Состояния задач: `planned`, `ready`, `in_progress`, `blocked`, `done`, `deferred`. Открытая issue сама по себе не означает готовность к выполнению.
- Перед началом следующего этапа проверить журнал контрольной точки. Не выполнять остальные задачи пакетом, если владелец попросил только одну.

## Определение готовности задачи

Критерии приёмки выполнены; необходимые проверки пройдены; изменения и ограничение объёма описаны; документация/API обновлены при изменении контракта; отсутствуют секреты в артефактах; обновлены issue, журнал, статус и пояснительная записка. Отдельно указать, что не проверено из-за отсутствия оборудования, аккаунтов или облака. Невыполненный обязательный критерий оставляет задачу открытой.

## Как исполнять короткую команду

На «Сделай PM-014» открыть соответствующий Markdown и issue, перечитать этот регламент, проверить зависимости и контрольную точку. Если всё готово — сразу выполнять. Если зависимость отсутствует — назвать конкретный блокер и продолжать только независимую подготовку, не выдавая её за завершение задачи.
