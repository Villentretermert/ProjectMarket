## Как проверяли

Образ соответствует поставке `68958f1` и полному SHA-256 в JSON. Внутри установлены libpq `18.6-1.pgdg12+2`, libldap `2.5.13+dfsg-5` и GnuTLS `3.7.9-2+deb12u7`. Отдельные дочерние процессы от UID 10001 вызывали настоящий `marketob_api.health.database_status` и загруженные библиотеки Debian. Стенд работал с файловой системой только для чтения, временным каталогом в памяти и сетью loopback. Сертификаты и данные каталога созданы для эксперимента.

LDAP-стенд отвечал на bind и search. В качестве безопасного контрольного значения он возвращал `application_name=ldap_probe_marker`. Приёмник PostgreSQL разбирал параметры стартового пакета и закрывал соединение до аутентификации. Поэтому ожидаемое значение readiness стенда — `unavailable`. Наличие метки в стартовом пакете показывает, что приложение действительно использовало ответ каталога. Поле `wire` содержит события первичного соединения, `referral_wire` — перенаправленного, `pg_wire` — приёмника PostgreSQL.

## Отказ выделения памяти

Файл `pg_service.conf` с записью `ldap://` привёл из readiness через libpq в `ldap_init`, затем в `ldap_url_parsehosts`. Диагностический модуль ограничивал инъекцию именем функции, аргументом и тестовым узлом. При копировании строки схемы одна функция вернула NULL. Дочерний процесс завершился по assertion с SIGABRT до сетевого обмена. Обычные вызовы того же сервиса, в том числе с выключенным модулем, дошли до PostgreSQL с ожидаемым параметром. [Вызов LDAP из libpq](https://github.com/postgres/postgres/blob/REL_18_6/src/interfaces/libpq/fe-connect.c) и [исправление OpenLDAP для списка хостов](https://github.com/openldap/openldap/commit/6563fab9e2feccb0a684d0398e78571d09fb808b).

Два отдельных вызова библиотеки проверили копирование IPv6-адреса в скобках и открытие локального LDIF-файла через URI `file://`. Каждый обычный вызов прошёл, каждый адресный отказ привёл к SIGSEGV. При передаче IPv6-адреса в URL файла службы libpq отклонил порт до входа в этот обработчик. Использование LDIF относится к прямой проверке библиотеки. Штатные параметры базы берутся из настроек оператора. [Исправление обработки LDIF](https://github.com/openldap/openldap/commit/752d320cf96e46f24c0900f1a8f6af0a3fc3c4ce) и [состояние пакета Debian](https://security-tracker.debian.org/tracker/CVE-2023-2953).

## Идентификация LDAP-сервера

Для проверки TLS использовался доверенный тестовый CA и обязательная проверка сертификата. Прямой LDAPS-клиент принял правильный DNS SAN, отверг сертификат с полностью чужим именем и при настройке библиотеки по умолчанию принял чужой SAN с подходящим CN. Все проверки TLS и перенаправлений выполнены без диагностического модуля выделения памяти. [Проверка имени в GnuTLS-реализации OpenLDAP](https://github.com/openldap/openldap/blob/OPENLDAP_REL_ENG_2_5_13/libraries/libldap/tls_g.c).

Первичный URL `ldaps://` в файле службы libpq отклоняется. Указание `ldap://` запускает анонимный bind. В варианте по умолчанию наблюдался bind LDAPv2. Полученный ответ с перенаправлением формата v3 не привёл к соединению со вторым узлом в этих проверках. При `LDAPVERSION=3` и включённых referrals второй узел получил LDAPS-соединение.

| Сертификат второго узла | Настройка SAN | Наблюдение в цепочке приложения |
| --- | --- | --- |
| SAN правильный | По умолчанию | Bind, search, метка в PostgreSQL |
| SAN чужой, CN правильный | По умолчанию | Bind, search, метка в PostgreSQL |
| SAN чужой, CN правильный | `LDAPTLS_REQSAN=demand` | TLS-соединение закрыто до bind. Стартового пакета PostgreSQL нет |
| SAN правильный | `LDAPTLS_REQSAN=demand` | Bind, search, метка в PostgreSQL |

Для профиля, где оператор требует совпадения SAN, проверена комбинация доверенного CA, `LDAPTLS_REQCERT=demand` и `LDAPTLS_REQSAN=demand`. Она защищает проверку личности второго узла. Первичный поиск в данном эксперименте использовал обычный LDAP. Его доверие нужно оценивать отдельно. Оператору локального пилота достаточно прямого адреса базы из Compose. [Описание условий CVE в Debian](https://security-tracker.debian.org/tracker/CVE-2020-15719).
