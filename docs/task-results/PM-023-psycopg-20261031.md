## Что именно проверяет код

После импорта ssl, затем psycopg, Python3.14
[`ctypes.util.dllist`](https://docs.python.org/3.14/library/ctypes.html#ctypes.util.dllist)
даёт фактически загруженные библиотеки текущего процесса. Их абсолютные пути
сверяются с RECORD inventory установленного psycopg-binary. Только совпавшие
libpq/libssl/libcrypto попадают в результат; копия на диске без факта загрузки
не считается использованной. Из загруженной libcrypto читается OpenSSL_version,
для трёх файлов вычисляются SHA-256. Публичный JSON содержит только имена файлов.

Результат `complete` требует ровно одну прочитанную библиотеку каждого вида.
Ошибки loader/чтения, относительный путь, неоднозначность, отсутствие metadata
или другая implementation дают `incomplete` и exit2. Exit0 означает полноту
**этого inventory**, а не отсутствие уязвимостей. Поле security_assessment
остаётся not_performed. Скрипт не соединяется с БД, не читает конфигурацию MarkeTOB,
не запускает сервер и не изменяет зависимости. Это отдельный процесс inspection,
не снимок памяти уже работающего API и не полный SBOM всех native consumers.

## Разбор OpenSSL

Статический этап до runtime-проверок сохранил один вход Linux bundled SSL /
CVE-2026-84782: **needs_review**, rank1, confidence medium.
[Контракт с evidence/gaps](assets/PM-023/psycopg-20261031/static-triage.json).
Применимого SECURITY.md для apps/api resolver не обнаружил.

Уязвимость требует DTLS retransmission при приостановленной записи handshake;
исправленные upstream ветки —3.5.9 и3.6.5. Обнаруженные3.5.8 и3.6.4 входят
в затронутые диапазоны. Это не доказывает эксплуатацию MarkeTOB.
[OpenSSL advisory](https://openssl-library.org/news/secadv/20260929.txt).

MarkeTOB получает PostgreSQL DSN из конфигурации оператора. Путь
Settings → ConnectionPool/psycopg.connect → libpq18.6 использует TCP stream
и TLS context в
[fe-secure-openssl.c](https://github.com/postgres/postgres/blob/REL_18_6/src/interfaces/libpq/fe-secure-openssl.c#L753)
и [fe-connect.c](https://github.com/postgres/postgres/blob/REL_18_6/src/interfaces/libpq/fe-connect.c#L2859).
DTLS-путь здесь не установлен. Это scoped контрдоказательство для прямого Linux
libpq consumer; оно не закрывает все bundled native consumers, Windows18.4
или остальные OpenSSL advisory. PoC/эксплуатация не воспроизводились.

На дату проверки [стабильная версия psycopg](https://www.psycopg.org/psycopg3/docs/news.html)
по-прежнему3.3.6;3.3.7 unreleased. Поэтому обновление pin сейчас не решает
bundled SSL. Поддерживаемая альтернатива —
[`psycopg[c]`](https://www.psycopg.org/psycopg3/docs/basic/install.html#local-installation)
с системными libpq/SSL. Её ещё не собирали и не устанавливали.

Следующий подэтап: проверить отдельный Linux-кандидат C implementation с
сохранением libpq18.6, поддерживаемым системным SSL, воспроизводимыми pins,
проверкой TLS/certificate validation, pools/transactions/recovery и полного CI.
Нельзя просто заменить wheel DLL/SO или объявить Python ssl версией драйвера.
Windows binary остаётся отдельным охватом; потенциальные изменения GSSAPI,
сертификатов и native prerequisites должны быть проверены до замены поставки.
